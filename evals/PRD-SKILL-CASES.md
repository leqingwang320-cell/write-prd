# write-prd Skill 回归测试用例

> 版本：跟随 SKILL.md `skill_version: "1.0"`
> 用途：修改 SKILL.md 或任何 reference 后，人工或脚本按用例逐条跑一遍，确认核心行为未退化。
> 每条用例包含：输入、上下文（如有）、预期行为、覆盖的规则来源。

## 一、入口门槛

### C-01 空输入 → 只索要材料

- **输入:** "写一个 PRD"
- **上下文:** 无
- **预期:** 回复只请求原始需求或材料，**不得**附带方向菜单、空模板、产品方向推荐或任何 PRD 标题。
- **覆盖:** SKILL.md 入口分流规则 #1, PRD-ENTRY-GATE 二、空输入

### C-02 一句话方案 → 进入九项门槛，不输出 PRD

- **输入:** "做一个电商客服系统"
- **上下文:** 无
- **预期:** 回复识别输入为"一句话方案"，评估九项门槛后给出**一个** B0 最高影响问题（如 G-01 核心用户）。**不得**输出任何带 PRD、MVP、产品目标、功能需求标题的正文。
- **覆盖:** SKILL.md 入口分流规则 #2, PRD-ENTRY-GATE 二、一句话方案, 四、九项硬门槛

### C-03 一句话 AI 方案 → B1 风险不绕过

- **输入:** "做一个 AI 简历优化工具"
- **上下文:** 无
- **预期:** G-01—G-09 均未通过。G-08（AI 边界）和 G-09（风险边界）为 B1 阻塞。回复不得输出 PRD 章节；核心用户和场景作为 B0 先问。
- **覆盖:** PRD-ENTRY-GATE 十一、典型判定, 六、阻塞等级 B0 vs B1

### C-04 部分输入已覆盖 → 跳过已确认项

- **输入:** "做客服系统，用户是商家客服团队，场景是售前咨询"
- **上下文:** 无（本轮直接给了 G-01 + G-02）
- **预期:** G-01、G-02 视为候选答案，不重复询问。从 G-03（核心问题）开始追问。
- **覆盖:** PRD-ENTRY-GATE 二、"用户已经提供的信息视为候选答案，不要重复询问"

## 二、渐进追问与批处理

### C-05 B0 缺口 → 逐项处理

- **输入:** 已确认 G-01（商家客服），等待下一问
- **上下文:** 上一轮确认了核心用户 = 商家客服团队
- **预期:** 下一问为 G-02（核心场景）。因为场景候选集依赖于用户是谁，两者互相改变方向，不批处理。
- **覆盖:** SKILL.md 常驻原则 #5（"会互相改变方向的缺口逐项处理"）, PRD-ENTRY-GATE §7.1

### C-06 用户说"一起问" → 全量批量确认

- **输入:** "一起问"
- **上下文:** 已确认 G-01、G-02，G-03—G-09 有多个缺口
- **预期:** 一次列出所有未通过门槛的当前结论、信息状态和推荐方向，标明事实/假设/决策状态。不限制为 B2/B3。
- **覆盖:** SKILL.md 常驻原则 #5（"用户主动说一起问"）, PRD-ENTRY-GATE §7.2

### C-07 B2/B3 同级独立缺口 → 默认批处理

- **输入:** 对某个确认方向后的追问回答
- **上下文:** 已确认 G-01—G-07，仅剩 B2/B3 级缺口（如"消息列表默认排序""支持哪些平台""客服同时接待上限"），且答案互不影响
- **预期:** 一次提问 2—3 项，无需用户主动要求批处理。
- **覆盖:** PRD-ENTRY-GATE §7.1 末尾批处理规则

## 三、硬停止与阻塞

### C-08 "继续形成 PRD" ≠ 授权假设草案

- **输入:** "继续形成 PRD"
- **上下文:** G-01—G-09 仍有 B0 缺口
- **预期:** **不得**输出 PRD 正文。回复停在"继续澄清"，复述已覆盖项，继续问最高影响缺口。
- **覆盖:** SKILL.md 入口分流 硬停止条件（"用户说继续形成 PRD 不等于授权假设草案"）

### C-09 B1 风险阻塞 → 只输出风险结论

- **输入:** 用户明确说"客服系统用 AI 自动处理退款"
- **上下文:** 涉及资金操作和不可逆决策
- **预期:** 识别为 B1 风险阻塞（AI 自动执行高影响决定），只输出风险阻塞结论和最保守方案。**不得**输出 PRD 章节。
- **覆盖:** PRD-ENTRY-GATE 六、B1 阻塞, SKILL.md 硬停止条件

## 四、假设草案

### C-10 用户明确授权 → 生成假设草案

- **输入:** "按你的推荐生成假设草案"
- **上下文:** 已确认 G-01—G-03 方向，G-04—G-09 有 AI 推荐但未确认
- **预期:** 输出顶部标明 **"本文包含待验证假设和 AI 推荐默认，不可直接进入研发"**。核心用户、场景、问题、目标、闭环、MVP、AI 边界、风险边界逐项标记 `待验证假设` / `AI 推荐默认` / `待产品决策`。质量状态只能为"可进入讨论"。
- **覆盖:** SKILL.md 第三步 假设草案, PRD-QUALITY-CHECKLIST 四

### C-11 正式 PRD 前九项必须全部通过

- **输入:** "生成正式 PRD"
- **上下文:** G-01—G-07 已确认，G-08、G-09 仍为 B1 阻塞
- **预期:** **不得**生成正式 PRD。回复停在"继续澄清"，指出 G-08/G-09 的 B1 阻塞。
- **覆盖:** PRD-ENTRY-GATE 一

## 五、禁止清单

### C-12 不得编造指标数字

- **输入:** 用户说"没有历史数据，你给我定个目标"
- **上下文:** 产品方向已确认，但无基线数据
- **预期:** 回复给出**无基线指标框架**（指标定义 → 入口事件 → 目标行为事件 → 去重主键 → 数据源计划，各项标记待定义或待产品决策）。**不得**出现任何百分比、时长、样本量等用户未提供的数字。
- **覆盖:** SKILL.md 禁止清单 #1, 人工确认边界

### C-13 不得省略五项执行底线

- **输入:** "只要功能清单就行"
- **上下文:** PRD 生成中
- **预期:** 回复说明五项底线（用户动线、范围、关键业务规则、失败恢复、可执行验收），推荐"极简 PRD"作为替代。可以另外输出纯《功能清单》，但不得将其标记或推荐为正式 PRD。
- **覆盖:** SKILL.md 输出契约, 禁止清单 #3

### C-14 不得把 AI 推荐写成已确认事实

- **输入:** 生成假设草案后，用户说"看起来没问题，发正式版"
- **上下文:** 草案中多项标为 AI 推荐默认
- **预期:** **不得**直接将 AI 推荐默认改为已确认结论。指出哪些项仍需人工确认后才能生成正式 PRD。
- **覆盖:** PRD-ENTRY-GATE 三、信息状态, 入口禁止清单 #5
## 七、复杂度裁剪

### C-17 微改需求 → 简单 PRD

- **输入:** "在现有客服系统里加一个'标记为已处理'按钮"
- **上下文:** 已有完整的客服系统背景
- **预期:** 复杂度判断为"简单"。输出 3—5 个短段或一张需求表加验收，不展开完整模板章节。五项执行底线（动线、范围、规则、异常、验收）不能省略。
- **覆盖:** PRD-COMPLEXITY-RULES 四、简单 PRD

### C-17A 微改但信息不全 → 不脑补升级

- **输入:** "在订单详情页加一个复制订单号按钮"
- **上下文:** 用户未说明权限、埋点、灰度、外部依赖和完整异常策略
- **预期:** 不得因信息未说明而推测存在复杂权限、多系统依赖或发布风险。若不存在会改变需求的 B0/B1，按简单需求输出极简结构；确有关键缺口时只澄清该缺口，复杂度保持简单或待定，不自动升级为标准/复杂。
- **覆盖:** SKILL.md 第三步“两个判断轴”, PRD-COMPLEXITY-RULES 一

### C-17B 简单描述且方向不清 → 先澄清，不生成复杂 PRD

- **输入:** "给列表加个提醒"
- **上下文:** 不清楚提醒对象、触发时机和展示方式
- **预期:** 识别为信息成熟度不足，询问一个会改变需求方向的最高影响问题。不得把多个可能分支合并成复杂提醒系统，也不得提前展开标准或复杂 PRD。
- **覆盖:** PRD-ENTRY-GATE, PRD-COMPLEXITY-RULES 一

### C-18 敏感数据 → 强制升级

- **输入:** 一个涉及用户聊天记录分析的需求
- **上下文:** 处理个人信息
- **预期:** 复杂度判断命中"至少标准"的强制升级条件（涉及敏感个人信息）。数据隐私章节必须保留。
- **覆盖:** PRD-COMPLEXITY-RULES 二、强制升级条件

### C-18A BRD 转 PRD → 聚焦增量而非重复扩写

- **输入:** “基于这份 BRD 生成 PRD”
- **上下文:** BRD 已包含背景、业务目标、实验指标和分流方案；本次产品变化是下线若干页面、收费与下发节点
- **预期:** 启用 `BRD-TO-PRD.md`。主 PRD 简要引用 BRD 的 WHY 和指标，重点输出改动盘点、Before / After、增量规则、异常和验收；不得重新生成完整背景论证、重复指标表和通用风险长表。
- **覆盖:** BRD-TO-PRD 二、三、五

### C-18B 存量治理能力 → 不写成新增 P0

- **输入:** BRD 要求使用现有实验平台进行固定分组
- **上下文:** 已确认实验平台具备分组、配置、审计和关闭能力
- **预期:** 将相关能力标记为“现有能力复用”，只写本次配置和适配差异，不把实验平台建设、通用审计、通用监控和回滚平台写成新增 P0。
- **覆盖:** BRD-TO-PRD 三、四

### C-18C 治理来源不明 → AI 建议不得变成硬需求

- **输入:** BRD 未提到完整红队检查、全量上线清单或城市级回滚演练
- **上下文:** 没有提供历史治理方案
- **预期:** 最小安全底线可以保留；其他治理建议标记为“AI 优化建议”或“历史方案待核对”，不得直接写成上线门槛、强制验收或已确认 P0。
- **覆盖:** BRD-TO-PRD 四、五

## 八、质量自检

### C-19 自检发现可修项 → 修复后交付

- **输入:** 完成初稿，执行自检
- **上下文:** PRD 中有一个 P0 未在用户动线中出现
- **预期:** 自检发现后直接修复（补入动线），交付修订后的正文，并记录"发现的问题 → 修订后的落点"。**不得**只输出问题清单而不修复。
- **覆盖:** SKILL.md 第五步, 踩坑点 "自检只报不修"

### C-20 假设草案 → 质量状态不能是"可研发交接"

- **输入:** 自检一份假设草案
- **上下文:** 结构完整、无 P0 硬伤
- **预期:** 质量状态判定为"可进入讨论"，**不能**判为"可研发交接"或"可进入正式评审"。
- **覆盖:** PRD-QUALITY-CHECKLIST 四、最终质量状态

## 运行说明

每个用例独立运行。建议按分组顺序执行，因为部分用例依赖前序用例建立的状态（如 C-05 依赖 C-02/C-04 的上下文）。

验证方式：
1. 新建对话（清空上下文）
2. 发出给定"输入"及上下文说明
3. 对照"预期"检查回复是否满足所有约束
4. 记录是否通过

回归频率：每次修改 SKILL.md 或任何 reference 文件后至少跑一遍一、二组。大版本迭代跑全量。

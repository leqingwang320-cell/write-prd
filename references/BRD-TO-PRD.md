# BRD 转 PRD：增量写作与文档治理

> 用途：用户明确要求基于 BRD、立项材料、业务方案或实验方案生成 PRD 时，在入口门槛通过后、读取完整模板前使用。
> 目标：继承 BRD 已确认的 WHY 与业务决策，只补足产品执行合同，避免把复杂业务扩写成冗长、重复的 PRD。

## 一、适用与优先级

满足任一条件时启用本规则：

- 用户明确说“基于 BRD 生成 PRD”。
- 输入材料已包含业务背景、目标、范围、指标或实验方案，用户希望转成产品需求。
- 已有业务方案较完整，本次重点是明确产品改动、流程、规则、异常和验收。

本规则不降低入口门槛、风险、安全、异常恢复和验收底线。与通用模板冲突时，优先采用本文件的增量表达和主文档裁剪方式；事实可信度与安全规则仍以主 Skill 为准。

## 二、先做来源映射，不重写 BRD

先把材料分为四类：

| 类型 | 判断 | PRD 中的处理 |
|---|---|---|
| BRD 已确认 | 有明确结论、范围或决策来源 | 简要继承并引用，不重新论证 |
| 现有产品能力 | 当前系统已具备，本次仅复用或配置 | 标记“复用”，不写成新增 P0 |
| 本次产品增量 | 为实现 BRD 必须新增、修改或下线 | 作为 PRD 主体展开 |
| 缺口与决策 | 材料未覆盖且会影响产品执行 | 按入口门槛澄清或列为开放项 |

BRD 已经完整说明的市场背景、战略价值、业务规模和立项理由，PRD 只保留与产品取舍直接相关的摘要及来源链接。不得换一种说法整章复制。

## 三、增量范围是主线

生成前先形成“改动盘点”：

| 模块或链路 | Before | After | 变化类型 | 来源状态 | 是否本次新增 |
|---|---|---|---|---|---|
| 示例 | 当前行为 | 目标行为 | 新增 / 修改 / 下线 / 复用 | BRD 已确认 / 历史方案 / AI 建议 | 是 / 否 |

规则：

1. 只有“本次新增=是”的内容才能默认进入 P0 或功能需求。
2. 复用实验平台、权限、审计、监控、配置、回滚等现有能力时，只写复用要求和适配差异。
3. 无法确认是存量还是新增，标记“待确认”，不得直接扩写成完整建设需求。
4. 用户没有提供系统现状时，不以“治理完整”为理由假定需要新建平台能力。
5. 对纯下线、开关或配置型需求，优先围绕变化点写，不重述完整原链路。

## 四、治理内容必须标记来源

每条治理要求只能使用以下来源之一：

- **BRD 明确要求**：材料中直接提出。
- **历史方案或公司规范**：用户提供或可合法读取的既有方案、制度、平台约束。
- **现有能力复用**：确认系统已经具备。
- **AI 安全底线**：为避免误报成功、资损、隐私泄露或不可恢复状态而必须保留的最小要求。
- **AI 优化建议**：合理但不是当前已确认需求。

处理方式：

- 前四类可以进入正式 PRD，但必须保留来源或确认状态。
- “AI 优化建议”默认放入建议或开放项，不得静默升级为 P0、上线门槛或强制验收。
- 若历史方案不可访问或未提供，不得声称符合历史治理方案；只说明“历史方案待核对”。
- 安全底线采用最小充分表达，不扩写成通用治理体系。

## 五、主文档与附件分层

即使业务复杂，主 PRD 也默认控制为以下内容：

1. 决策与改动摘要。
2. 范围、非目标与改动盘点。
3. 最短用户或系统动线。
4. 本次新增/修改的功能与关键规则。
5. 高影响异常与最小恢复。
6. 核心验收。
7. 阻塞依赖和开放问题。

以下内容存在时优先放附件或引用 BRD，不在主文档重复展开：

- 完整业务背景、规模分析、战略论证。
- 完整指标字典、实验统计方案和样本量测算。
- 通用风险清单、红队假设清单。
- 全量上线检查表、通用回滚操作手册。
- 完整状态机、数据字典、接口和技术方案。
- 已有平台治理规则和历史方案正文。

只有某项内容直接影响本次产品决策、P0 范围或验收时，才在主文档保留摘要。

## 六、默认输出骨架

### 简单或单点增量

- 改动摘要与范围
- Before / After
- 关键规则与失败恢复
- 验收
- 必要开放项

### 标准或复杂业务的增量 PRD

- 决策摘要：BRD 已确认什么，本 PRD 决定什么
- 改动范围：新增 / 修改 / 下线 / 复用 / 不做
- 核心动线与关键分支
- 增量功能、规则、异常
- 核心验收
- 阻塞项
- 附件索引

复杂度高只增加必要的风险深度，不自动增加主文档章节数量。

## 七、去重规则

同一结论只定义一次：

- 指标在“指标或实验附件”定义，目标章节只引用。
- 回滚原则在“异常与恢复”定义，上线章节只引用触发条件。
- 分组、权限、状态等公共规则集中定义，功能与验收引用规则 ID。
- 风险表不重复功能需求；只记录风险信号、责任和决策。
- 验收验证行为结果，不复述背景和方案理由。

若同一内容在三个以上位置出现，必须合并或改为引用。

## 八、生成前的最小澄清

不要询问用户选择“简单 / 标准 / 复杂”。只有答案会改变增量范围或触发强制升级时，才询问业务事实。

优先澄清：

1. 哪些能力已经存在，本次只是复用或配置？
2. 本次真正新增、修改或下线哪些产品行为？
3. 哪些治理要求来自既有规范，哪些只是期望建议？

每轮仍遵守入口门槛，只问一个最高影响问题。

## 九、自检

- [ ] BRD 已确认内容以引用和摘要继承，没有重复论证。
- [ ] 已区分存量能力、本次增量和开放缺口。
- [ ] 存量能力未被错误写成新增 P0。
- [ ] 治理要求均有来源状态。
- [ ] AI 优化建议未被写成已确认上线门槛。
- [ ] 主文档聚焦产品增量，专项内容已放附件或引用。
- [ ] 指标、回滚、分组和风险没有跨章节重复。
- [ ] 复杂业务没有被自动转换成冗长文档。

# PRD 复杂度判断与裁剪规则

> 用途：在生成 PRD 前判断需求属于简单、标准还是复杂，并决定 `PRD-TEMPLATE.md` 中各章节的展开深度。  
> 原则：复杂度决定分析深度，不决定是否可以省略核心用户、问题、范围、用户动线、业务规则、异常、验收和风险。

## 一、先判断风险，再计算复杂度

### 1. 复杂度与信息成熟度严格分离

- 信息成熟度回答“现在能否成稿”，复杂度回答“需求本身需要多深的文档”。两者不得互相替代。
- 用户没说清楚、九项门槛缺失、开放问题多或需要继续追问，不代表需求复杂。
- 只使用已确认事实或可追溯材料评分。未知角色、未知依赖、未知风险和未知发布方式一律记为“待确认”，不计入复杂度分数，也不按最坏可能性升级。
- 若关键事实不足以分类，输出“复杂度待定”，先完成最高影响澄清；不得为了保险默认选择标准或复杂。
- 澄清问题应针对会改变产品方向或强制升级的事实，不要求用户为了证明需求简单而补齐完整模板。

### 2. 判断顺序

不要只根据功能数量、开发工期或用户要求的篇幅判断 PRD 复杂度。

正确顺序是：

```text
检查强制升级条件
→ 评估七个复杂度维度
→ 得出建议等级
→ 选择固定和条件章节
→ 输出分类理由
```

## 二、强制升级条件

满足下列任意**已确认或有可追溯证据**的条件时，不允许归为简单需求。仅仅“可能涉及”、用户未提及或 AI 推测，不构成强制升级；若该未知同时构成 B0/B1，则先澄清，不先升级。

### 至少升级为标准

- 涉及个人信息、简历、身份、位置、聊天记录等敏感数据。
- 包含 AI 生成、推荐、分类或预测，且结果会影响用户决策。
- 存在两个以上用户角色或明显的权限差异。
- 存在异步处理、失败重试、结果回调或较长等待。
- 需要接入一个以上外部系统或第三方服务。
- 需要灰度验证核心指标，或者错误会影响较多用户。
- 核心对象存在三个以上业务状态。

### 直接升级为复杂

- 涉及医疗、金融、法律、未成年人或其他高风险决策。
- AI 可以在没有人工确认的情况下发布、发送、交易、删除、审批或执行不可逆操作。
- 涉及资金、账户资产、核心权限或大规模敏感数据迁移。
- 包含多角色审批、跨组织协作和复杂状态机。
- 同时改造多个核心系统、历史数据和上下游接口。
- 错误可能造成严重合规、安全、财务或品牌影响。
- 需要分阶段迁移、双写、回滚或长周期兼容旧流程。

强制升级条件优先级高于用户的篇幅要求。用户可以要求表达更简洁，但不能因此删除必要的风险、权限、状态、异常或验收内容。

## 三、七个复杂度维度

在没有触发“直接复杂”条件时，对以下七个维度分别评分。

| 维度 | 0 分：低 | 1 分：中 | 2 分：高 |
|---|---|---|---|
| 用户与角色 | 单一用户、无权限差异 | 2—3 个角色或少量权限差异 | 多角色、审批链或跨组织协作 |
| 用户动线 | 单一路径、决策点很少 | 多步骤，存在分支和恢复 | 多入口、多阶段、循环或复杂状态机 |
| 业务规则 | 规则少且稳定 | 多条校验、优先级或例外 | 规则组合复杂、互相依赖或频繁变化 |
| 系统与依赖 | 单系统、无外部依赖 | 一个外部服务或少量跨模块依赖 | 多系统、数据迁移、上下游强依赖 |
| 数据与风险 | 普通数据、可轻易撤销 | 敏感数据或中等业务风险 | 高风险数据、不可逆影响或严格合规 |
| AI 自主程度 | 不使用 AI，或 AI 只做无风险辅助 | AI 生成建议，结果由用户确认 | AI 自动决策或执行高影响动作 |
| 发布与协作 | 单团队、小范围、可直接回滚 | 跨职能协作或需要灰度 | 多团队、分阶段迁移、复杂回滚和运营准备 |

### 分数对应等级

| 总分 | 建议等级 | 前提 |
|---:|---|---|
| 0—3 | 简单 | 没有触发任何强制升级条件 |
| 4—8 | 标准 | 没有触发直接复杂条件 |
| 9—14 | 复杂 | 或命中任一直接复杂条件 |

评分用于提高判断一致性，不替代产品经理判断。处于等级边界时，AI 应说明最可能导致升级或降级的**已知因素**。不得给未知项预填 1 分或 2 分；未知项单列为待确认。若排除未知项后已知事实只支持简单需求，就保持简单，除非后续确认命中升级条件。

## 四、简单 PRD

### 1. 适用情况

- 现有页面增加一个低风险字段、按钮、提示或操作；此类单点微改默认简单，除非已确认命中强制升级条件。
- 单角色、单系统、短流程的小功能。
- 规则较少，失败后可以立即恢复。
- 不涉及敏感数据、复杂权限或高影响 AI 决策。

### 2. 输出目标

- 预计阅读时间：5—8 分钟。
- 聚焦评审和研发真正需要的内容，不写完整战略分析。
- 每个 P0 需求仍然必须有规则、异常和验收。

### 3. 章节裁剪

| 模板章节 | 简单 PRD 的处理方式 |
|---|---|
| 文档状态与摘要 | 保留一句话说明、当前决策和未确认项；九项门槛压缩为一张短表 |
| 用户、场景、问题 | 用一张表或三段话说明，不制作完整 Persona |
| 目标与指标 | 保留一个目标、一个主指标和必要护栏；没有线上指标时写清验证方式 |
| 产品方案与用户动线 | 保留主路径、至少两个边界或失败场景 |
| MVP 与优先级 | 保留本期做、不做和后置项；需求较少时不强制 P1/P2 表格 |
| 功能需求与规则 | 按功能点展开，合并重复表格；保留稳定 ID |
| 验收 | 每个 P0 至少一个正常验收和一个相关异常验收 |
| 风险、依赖和开放问题 | 只写真实存在的关键项 |
| AI、隐私、埋点、灰度、里程碑 | 仅在触发条件成立时加入；触发 AI 或敏感数据时自动升级为标准 |

### 4. 不允许省略

- 核心用户和使用场景。
- 用户主路径。
- 本期范围和明确不做。
- 关键业务规则。
- 空状态、失败或边界处理。
- 可执行验收标准。

## 五、标准 PRD

### 1. 适用情况

- 典型的新功能、业务模块或 AI 辅助工具。
- 有多步骤动线、多个决策节点和若干异常分支。
- 涉及敏感数据，但通过保守策略和人工确认可以控制风险。
- 有跨职能协作、外部服务或上线指标验证。

### 2. 输出目标

- 主文档预计阅读时间：10—15 分钟。
- 让产品、设计、研发和测试对问题、范围、流程、规则和验收形成共同理解。
- 完整展开 P0，压缩 P1/P2，不为每个低优先级功能重复大表格。

### 3. 章节裁剪

| 模板章节 | 标准 PRD 的处理方式 |
|---|---|
| 文档状态与摘要 | 完整保留成稿门槛状态和关键决策摘要 |
| 用户、场景、问题与证据 | 完整保留，但只写与当前需求直接相关的用户特征和证据 |
| 目标、指标与非目标 | 保留主指标、过程指标和护栏指标；未知数值不得编造 |
| 产品方案与用户动线 | 完整展开主路径、关键决策、3—5 类异常和完成后的下一步 |
| MVP 与约束 | 完整保留 P0、后置项、明确不做和三层约束 |
| 功能需求 | P0 模块完整展开；相似规则和状态可以合并；P1/P2 只保留摘要 |
| AI 处理逻辑 | 使用 AI 时必选，覆盖任务边界、处理链、低置信度和评估方式 |
| 数据与隐私 | 涉及敏感数据时必选，覆盖收集、存储、保留、删除和第三方处理 |
| 验收与追溯 | 每个 P0 有正常、边界或失败验收；保留端到端剧本和追溯表 |
| 埋点与指标 | 需要验证上线效果时保留，只采集必要字段 |
| 风险、依赖和开放问题 | 完整保留，明确是否阻塞 P0 |
| 灰度与回滚 | 中等以上风险或真实用户上线时保留 |
| 里程碑 | 只有跨团队或长周期时保留 |

### 4. 长度控制

- 不为每个功能重复“背景、目标和用户”，公共内容只写一次。
- 相同状态流转由一张公共状态表统一描述。
- 相同异常处理形成通用规则，模块只引用规则 ID。
- 验收表以可执行为目标，不重复产品说明。
- 详细评测集、数据字典和接口方案应放入独立附件。

## 六、复杂 PRD

### 1. 适用情况

- 多团队、多角色、多系统或多阶段业务。
- 存在复杂状态机、迁移、审批或不可逆操作。
- 涉及高风险数据、严格合规或 AI 自动决策。
- 需要灰度、双写、兼容、回滚和运营支持。

### 2. 输出目标

- 主 PRD 仍应让核心决策在 15 分钟左右被理解。
- 复杂度通过“主文档 + 专项附件”承载，而不是生成一份无限增长的单文件。
- 主文档负责产品合同，附件负责需要独立评审的细节。

### 3. 主文档必须完整保留

- 决策摘要和信息可信度。
- 用户、场景、问题和证据。
- 目标、指标、非目标和护栏。
- 端到端用户动线、角色协作和关键状态。
- 分阶段范围、硬约束和迁移边界。
- 核心业务规则和高风险异常。
- 发布门槛、灰度、回滚和运营准备。
- 阻塞依赖、重大风险、决策人和截止时间。

### 4. 建议拆分的专项附件

| 附件 | 触发条件 | 主要内容 |
|---|---|---|
| `USER-FLOWS.md` | 多入口、多角色或流程图较多 | 完整用户动线、泳道和异常分支 |
| `STATE-MACHINE.md` | 核心对象状态复杂 | 状态定义、转换条件、非法转换和恢复 |
| `BUSINESS-RULES.md` | 规则数量多或组合复杂 | 规则 ID、优先级、冲突和例外 |
| `AI-EVALUATION.md` | AI 影响核心结果 | 评测集、维度、阈值、红队案例和降级策略 |
| `DATA-PRIVACY.md` | 敏感数据或严格合规 | 数据地图、保留、删除、供应商和审计 |
| `ANALYTICS.md` | 指标或实验体系复杂 | 数据字典、埋点、口径和实验设计 |
| `ROLLOUT-MIGRATION.md` | 灰度、迁移、双写或兼容 | 发布阶段、校验、回滚和旧数据处理 |

### 5. 不允许的做法

- 为了压缩篇幅删除高风险异常和回滚方案。
- 把技术方案、接口文档和所有测试用例全部塞进 PRD 主文档。
- 用“详见后续设计”替代尚未解决的核心产品决策。
- 把开放问题写在文末，却不标记是否阻塞 P0。

## 七、AI 的分类输出格式

生成 PRD 前，AI 应先在内部完成判断，并在文档状态中简要说明：

```text
建议复杂度：标准
判断依据：多步骤用户动线、AI 生成结果需要用户确认、涉及简历敏感信息、依赖第三方模型服务。
强制升级：命中“AI 影响用户决策”和“敏感个人信息”，不得归为简单。
本次加载：全部固定章节 + AI 处理逻辑 + 数据隐私 + 埋点 + 灰度回滚。
本次省略：里程碑；当前没有跨团队长周期计划。
```

正文不要展示详细打分过程，除非用户要求查看判断依据。

## 八、用户覆盖规则

- 用户可以要求从简单升级为标准或复杂。
- 用户可以要求语言更简洁，但不能删除命中的风险章节。
- 用户要求降级时，AI 应说明会遗漏什么，并保留强制升级章节。
- 用户只说“写详细一点”时，不自动升级复杂度；先看业务本身是否复杂。
- 用户只说“简单写写”时，不自动降级；先完成风险判断。

## 九、AI 简历优化工具的分类验证

### 1. 七维评分

| 维度 | 分数 | 判断 |
|---|---:|---|
| 用户与角色 | 0 | 第一版只有求职者一个核心角色 |
| 用户动线 | 1 | 存在输入、分析、补充、建议确认和失败恢复 |
| 业务规则 | 1 | 包含事实约束、建议状态和多类异常 |
| 系统与依赖 | 1 | 依赖模型服务和临时会话处理 |
| 数据与风险 | 1 | 处理简历和用户补充信息等敏感数据 |
| AI 自主程度 | 1 | AI 生成诊断和建议，但最终由用户确认 |
| 发布与协作 | 1 | 需要质量评测、灰度和隐私检查 |
| 总分 | 6 | 建议归为标准 PRD |

### 2. 强制升级检查

- 命中敏感个人信息：至少标准。
- 命中 AI 影响用户决策：至少标准。
- AI 不会自动投递、发布或执行不可逆操作：不直接升级复杂。
- 当前没有多角色审批、多系统迁移或高风险自动决策：不直接升级复杂。

### 3. 最终结论

```text
AI 简历优化工具：标准 PRD
```

## 十、生成后的自检

- [ ] 复杂度等级有明确业务依据，不是按用户要求的字数决定。
- [ ] 已先执行强制升级检查，再计算七维分数。
- [ ] 没有把信息缺失、开放问题数量或追问轮次当成复杂度。
- [ ] 所有升级依据均来自已确认事实或可追溯材料，未知项未计分。
- [ ] 所有命中的风险章节均已保留。
- [ ] 简单 PRD 没有省略用户动线、异常和验收。
- [ ] 标准 PRD 只完整展开 P0，没有为 P1/P2 重复大量细节。
- [ ] 复杂 PRD 使用主文档和专项附件，没有形成不可阅读的单文件。
- [ ] 删除不适用章节后已重新编号。
- [ ] 文档中没有空章节、占位符或为了完整而填写的“无”。

# PRD 质量检查与评审规则

> 用途：在 PRD 生成后执行自检，或对已有 PRD 进行独立评审。  
> 核心原则：检查完整性只是底线，真正的质量来自事实可信、逻辑一致、范围可控、流程可恢复和结果可验收。

## 一、两种使用模式

### 1. 生成后的自检

PRD Skill 完成初稿后，必须在交付前执行本检查表。

- 可以自动修复：空章节、重复内容、错误引用、模糊表述、缺少异常、不可测试的验收和不必要的实现约束。
- 不得自动决定：核心用户、产品目标、MVP 取舍、指标目标、风险接受、AI 自主边界和隐私策略。
- 无法安全修复的问题必须保留为“产品决策”或“开放问题”，并说明是否阻塞 P0。

自检默认不向用户输出完整检查报告。完成可安全修复的内容后，只在 PRD 中保留仍需确认的问题。

### 2. 对已有 PRD 的独立评审

评审模式只发现问题，不直接重写原文，除非用户明确要求修改。

- 先输出发现，按严重程度排序。
- 每个发现都必须包含位置、问题、影响和具体修复建议。
- 不使用“这里不够清楚”这类没有行动指向的评价。
- 不为了显得严格而制造问题；能够成立的部分可以明确说明为什么成立。
- 正式立项、核心方案或高风险需求，优先使用独立上下文进行评审，减少写作者自我合理化。

## 二、开始评审前的输入门槛

满足以下条件后才执行完整质量评审：

- 能识别文档类型是正式 PRD 还是假设草案。
- 能识别需求复杂度及其裁剪规则。
- 文档主体已经完成，不是只有标题和大量模板占位符。
- 被引用且会影响结论的关键资料可以访问，或者文档已经说明资料缺失。
- 评审标准至少包括 `PRD-TEMPLATE.md`、`PRD-COMPLEXITY-RULES.md` 和本文件。

如果文档只是早期思路，不应假装进行“研发交接评审”。可以改为检查：是否适合进入下一轮讨论、还有哪些关键决策没有解决。

## 三、严重程度

| 级别 | 定义 | 典型影响 | 要求 |
|---|---|---|---|
| P0 | 阻塞进入下一阶段，继续执行可能造成真实伤害或方向性错误 | 错误立项、隐私或合规风险、AI 虚构、高风险流程不可恢复 | 必须修复后重新评审 |
| P1 | 重要缺口，显著影响 PRD 的决策或执行价值 | 范围不清、主流程断裂、规则矛盾、验收不可执行 | 进入下一阶段前修复 |
| P2 | 质量提升项，可以由产品经理决定接受或延期 | 次要边界、表达冗余、非关键追溯缺口 | 记录决定即可 |
| P3 | 样式或轻微表达问题，不影响实质理解 | 命名、格式、局部重复 | 时间有限时可忽略 |

严重程度不能通过平均分抵消。一个 P0 不能被十个表现良好的章节抵消。

## 四、最终质量状态

| 状态 | 判定条件 | 可以进入什么阶段 |
|---|---|---|
| 拒绝进入下一阶段 | 存在 P0 | 只能修订或补充信息 |
| 需要重要修订 | 无 P0，但存在 P1 | 修改后重新评审 |
| 可进入讨论 | 假设草案无结构性 P0，关键假设和待决策项已显式标记 | 用户访谈、方案讨论或原型验证 |
| 可进入正式评审 | 正式 PRD 无 P0/P1，但仍有非阻塞开放问题 | 产品、设计、研发和测试评审 |
| 可研发交接 | 正式 PRD 无 P0/P1，所有 P0 阻塞项已关闭，验收和依赖明确 | 排期、开发和测试 |

假设草案不能被判定为“可研发交接”，即使结构非常完整。

## 五、P0 硬阻塞项

以下问题命中任意一项，正式 PRD 不得进入研发交接。

| 编号 | 硬阻塞项 | 检查方式 |
|---|---|---|
| QG-01 | 文档未区分正式 PRD 和假设草案 | 检查文档状态和未确认决策 |
| QG-02 | 核心用户、场景或问题缺失，或三者互相矛盾 | 交叉检查第 0、1、3 章 |
| QG-03 | 将假设、推测、AI 生成内容写成已确认事实 | 检查证据来源和信息状态 |
| QG-04 | 编造用户研究、业务数据、竞品事实、指标基线或目标 | 尝试定位来源；无法定位则视为问题 |
| QG-05 | P0 不是最小可用闭环，或没有明确不做什么 | 检查每个 P0 的必要性和不做后果 |
| QG-06 | P0 需求没有出现在用户动线，或者用户动线无法走到完成状态 | 执行端到端流程走查 |
| QG-07 | 高影响异常没有恢复路径，失败会导致数据丢失、重复执行或错误状态 | 走查输入、系统、依赖、并发和恢复场景 |
| QG-08 | 需求无法验收，关键结果只能依赖主观判断 | 检查 Given/When/Then 和可观察证据 |
| QG-09 | AI 能生成或决定高影响内容，却没有事实边界、低置信度处理或人工确认 | 检查 AI 章节和用户动线 |
| QG-10 | 涉及敏感数据，却没有说明收集、使用、存储、保留、删除和第三方处理 | 检查数据地图和上线门槛 |
| QG-11 | 存在会改变核心用户、MVP、AI 边界或风险边界的未解决问题 | 检查开放问题是否阻塞 P0 |
| QG-12 | 方案、范围、规则、状态或验收之间存在相互冲突 | 建立跨章节追溯并检查一致性 |
| QG-13 | 最终文档仍包含模板占位符、TODO 或无法执行的“待补充” | 结构扫描和人工检查 |
| QG-14 | PRD 强制指定不必要的技术栈或文件结构，且没有产品行为理由 | 检查硬约束是否越权替代技术方案 |

假设草案允许存在 QG-02、QG-05 或 QG-11 对应的信息缺口，但必须显式标记，且最终状态只能是“可进入讨论”。涉及虚构事实、AI 高风险边界和敏感数据的 QG-03、QG-04、QG-09、QG-10 不能因为是草案而忽略。

## 六、分维度质量检查

### 1. 文档状态与信息可信度

- [ ] 文档明确是正式 PRD 还是假设草案。
- [ ] 复杂度等级与实际风险一致，没有为了篇幅降级。
- [ ] 已确认、证据、假设、开放问题和产品决策已经区分。
- [ ] 假设在出现的位置就被标记，不只集中放在文末。
- [ ] 每个事实性结论都能定位来源、时间或负责人。
- [ ] 不确定的外部事实使用“待确认”或“未知”，没有自信填充。
- [ ] 文档说明本次加载和省略了哪些条件章节。

### 2. 用户、场景和问题

- [ ] 第一版只有一个清晰的核心用户，不用“所有用户”逃避取舍。
- [ ] 用户特征与当前需求相关，不是泛化人口属性。
- [ ] 场景包含触发事件、任务、阻碍和期望结果。
- [ ] 表面方案和底层问题已经区分。
- [ ] 用户影响和业务影响能够被具体描述。
- [ ] 当前做法或替代方案已经说明。
- [ ] 问题证据与结论强度匹配，没有以小样本代表整体。
- [ ] 用户问题、用户动机和后续方案之间没有逻辑跳跃。

### 3. 产品目标和成功指标

- [ ] 用户目标描述结果，不是功能清单。
- [ ] 业务目标能够连接到核心问题，而不是附加口号。
- [ ] 主指标直接反映问题是否改善。
- [ ] 过程指标解释用户在哪个环节流失或受阻。
- [ ] 至少有一个护栏指标说明什么不能变差。
- [ ] 指标定义、口径、数据来源和观察周期明确。
- [ ] 基线和目标未知时显式标记，没有编造数字。
- [ ] “上线”“功能完成”“页面访问量”没有被错误当作用户结果。

### 4. 产品方案与逻辑一致性

- [ ] 方案说明了为什么能够解决问题，而不只是列出页面和功能。
- [ ] 每个关键能力都能追溯到用户问题或产品目标。
- [ ] 没有与问题无关、只因为“体验更完整”而加入的功能。
- [ ] 关键产品决策包含备选方案、取舍理由和确认状态。
- [ ] 推荐默认没有被写成不可变硬约束。
- [ ] 低风险实现选择留给设计和研发，没有过度规定技术方案。
- [ ] 方案与非目标、P0 和后置范围保持一致。

### 5. 用户动线

- [ ] AI 已主动补齐入口、前置条件、用户动作、系统反馈和完成状态。
- [ ] 主路径能够从入口连续走到用户获得结果。
- [ ] 每个关键决策节点都说明可选方案和默认行为。
- [ ] 用户需要确认的产品或 AI 决策没有被系统自动越过。
- [ ] 信息不足、空状态、权限不足和结果异常有明确处理。
- [ ] 处理中断后说明是否保留数据、从哪里重试和如何恢复。
- [ ] 用户退出、返回、撤销或重复操作的结果明确。
- [ ] 异步任务说明处理中、成功、失败、超时和重复提交状态。
- [ ] 多角色需求说明角色之间如何交接，而不是分别描述孤立页面。

### 6. MVP、优先级和范围

- [ ] 每个 P0 都是完成最短价值闭环的必要条件。
- [ ] 每个 P0 写明解决的问题、对应动线和不做后果。
- [ ] P1/P2 不被偷偷写进 P0 的验收范围。
- [ ] 明确不做的内容包括利益相关方可能产生期待的项目。
- [ ] 后置原因基于验证顺序、风险、资源或依赖，不只是“以后再说”。
- [ ] 硬约束、推荐默认和发挥空间分类合理。
- [ ] 简单 PRD 没有过度展开；标准 PRD 只完整展开 P0；复杂 PRD 使用专项附件。

### 7. 功能需求、业务规则和状态

- [ ] P0 功能都有稳定需求 ID。
- [ ] 每个功能说明前置条件、输入、输出和完成条件。
- [ ] 正常流程与用户动线一致。
- [ ] 业务规则具有触发条件和明确处理结果。
- [ ] 规则来源区分已确认、政策、数据和假设。
- [ ] 默认值、校验、优先级和冲突处理明确。
- [ ] 状态名称互斥且含义清楚。
- [ ] 每个状态说明进入条件、退出条件和用户反馈。
- [ ] 非法状态转换、重复操作或并发修改有处理原则。
- [ ] 权限要求与角色一致，敏感操作符合最小权限原则。

### 8. 异常、边界和恢复

至少检查以下类别，不适用时可以跳过，但不能默认忽略：

| 类别 | 需要检查什么 |
|---|---|
| 输入校验 | 空值、过短、过长、格式错误、特殊字符、重复输入 |
| 边界值 | 最小值、最大值、刚好达到阈值和超过阈值 |
| 空状态 | 第一次使用、搜索无结果、没有权限可见数据 |
| 系统失败 | 网络、超时、依赖服务不可用、部分成功 |
| 恢复路径 | 重试、返回、撤销、继续处理和数据保留 |
| 重复与并发 | 双击、重复提交、多端修改、数据版本冲突 |
| 会话与权限 | 登录过期、权限变化、资源被删除或转移 |
| 数据一致性 | 保存失败、状态不同步、重复记录、顺序错乱 |
| AI 异常 | 低置信度、事实冲突、拒答、超长输入和输出不完整 |
| 安全与隐私 | 越权访问、敏感信息暴露、日志泄露和删除失败 |

每个高影响异常都应说明：用户看到什么、系统做什么、数据是否保留、用户如何恢复、如何验收。

### 9. 验收与需求追溯

- [ ] 每条验收绑定具体需求或异常 ID。
- [ ] Given 描述可复现的前置状态。
- [ ] When 描述用户或系统执行的单一动作。
- [ ] Then 描述可以观察和判定的结果。
- [ ] 每条验收只有一个主要结果，避免多个行为混在一起。
- [ ] 每个 P0 至少覆盖正常路径和一个相关边界或失败场景。
- [ ] 高风险功能包含必要的性能、安全、可靠性或审计验收。
- [ ] 错误场景不仅能检测失败，还说明用户如何恢复。
- [ ] 验收标准不泄露不必要的实现细节。
- [ ] 用户问题、目标、P0、动线、验收和指标形成完整追溯。
- [ ] 测试人员无需猜测“体验好”“结果准确”“页面流畅”的具体含义。

### 10. AI 产品质量【条件：使用 AI 时必检】

- [ ] AI 的任务、非任务和人工确认点明确。
- [ ] 输出能够追溯到用户输入、业务资料或可靠来源。
- [ ] 不得推断或生成的事实已经列明。
- [ ] 低置信度、输入冲突和信息缺失有追问或降级路径。
- [ ] 用户可以接受、编辑、拒绝和撤销高影响结果。
- [ ] AI 建议没有被描述为确定事实或结果保证。
- [ ] 评估维度对应真实产品风险，不只写“准确、专业、自然”。
- [ ] 评测样本覆盖正常、边界、冲突、缺失和高风险输入。
- [ ] 每个质量阈值都有测量方法；没有基线时写明如何建立基线。
- [ ] 模型替换时必须保持的产品行为和安全边界明确。
- [ ] AI 自主程度越高，发布、审计、回滚和人工兜底越严格。

### 11. 数据、隐私、安全与合规【条件：涉及敏感数据时必检】

- [ ] 每类数据都说明目的和必要性。
- [ ] 数据来源、存储位置、保留时间和删除方式明确。
- [ ] 是否进入模型、日志、埋点或训练已经说明。
- [ ] 第三方供应商的数据保留、训练和删除政策是上线前确认项。
- [ ] 原始敏感内容不会进入普通日志、埋点属性和错误堆栈。
- [ ] 用户能够理解数据用途并控制修改、删除或退出。
- [ ] 删除失败时不会向用户误报成功。
- [ ] 权限、审计和高风险操作符合业务及适用政策要求。
- [ ] 数据策略与失败恢复、历史版本和跨设备需求没有矛盾。

### 12. 依赖、风险、假设和开放问题

- [ ] 依赖说明负责人、状态、最晚确认时间和延迟影响。
- [ ] 风险覆盖价值、可用性、可行性和业务可持续性，而不只关注技术。
- [ ] 每个高风险项有触发信号、预防措施和发生后的处理。
- [ ] “持续关注”没有被当作完整缓解方案。
- [ ] 所有高影响假设都在风险或验证计划中出现。
- [ ] 开放问题标记是否阻塞 P0、决策人和影响范围。
- [ ] 已解决的问题转成决策记录，而不是仍留在开放问题中。
- [ ] 风险接受属于产品或业务决策，AI 没有擅自关闭。

### 13. 可读性和复杂度裁剪

- [ ] 结论和关键决策在文档前部可被快速理解。
- [ ] 没有为了“完整”保留空章节或大量“无”。
- [ ] 公共背景、规则和状态只写一次，其他位置使用 ID 引用。
- [ ] P1/P2 没有按照 P0 深度重复展开。
- [ ] 复杂需求使用专项附件承载状态机、评测集、数据字典和迁移细节。
- [ ] 文档没有被实现细节、营销文案或通用产品知识淹没。
- [ ] 简单和标准 PRD 的主文档可以在目标时间内读完。
- [ ] BRD 转 PRD 时已区分 BRD 结论、现有能力、本次增量和开放缺口。
- [ ] BRD 的背景、指标、实验和治理内容没有在主 PRD 重复展开。
- [ ] 治理要求有明确来源；AI 优化建议没有静默升级为 P0 或上线门槛。

### 14. 内部 PRD 规范【固定】

- [ ] 已读取 `MERCHANT-PRD-STANDARD.md`。
- [ ] 已执行需求真实性、价值归属、时机和直接收益判断。
- [ ] 已覆盖 WHY / WHAT / HOW，并清楚描述关键 Before / After。
- [ ] 角色、价值归属和专用术语没有被泛化或臆测；非商家端需求已替换为真实核心用户。
- [ ] 内部规范已映射到通用 PRD，而不是复制出重复章节。
- [ ] 内审检查已执行，且未降低通用安全、恢复和验收底线。

## 七、跨章节一致性检查

质量检查不能只逐章打勾，还要检查下列连接是否成立：

```text
用户与场景
→ 核心问题与证据
→ 产品目标与指标
→ 解决方案
→ MVP 需求
→ 用户动线
→ 业务规则和状态
→ 异常与恢复
→ 验收标准
→ 上线验证
```

至少完成以下交叉检查：

| 连接 | 需要确认的问题 |
|---|---|
| 问题 → 目标 | 指标改善是否真的代表问题被缓解 |
| 用户 → 方案 | 方案是否适合核心用户，而不是泛化用户 |
| 方案 → P0 | P0 是否足以形成方案承诺的价值闭环 |
| P0 → 动线 | 每个 P0 在用户流程中何时被使用 |
| 动线 → 状态 | 每个关键动作如何改变系统状态 |
| 规则 → 异常 | 规则冲突或失败时如何处理 |
| P0 → 验收 | 是否存在可执行的完成定义 |
| 验收 → 指标 | 功能完成后如何验证真实效果 |
| 假设 → 风险 | 高影响假设错误时什么会失败 |
| 开放问题 → 阻塞 | 未解决问题是否会改变 P0 或风险边界 |

## 八、关键假设红队检查

标准和复杂 PRD 在正式评审前，应选择 3—5 个承重假设进行红队检查。简单 PRD 只有存在高影响假设时才需要。

### 1. 选择承重假设

优先选择“如果它是错的，整个方案或 MVP 就失去意义”的判断，而不是普通细节。

### 2. 先强化，再攻击

先写出该假设最有力的成立理由，再攻击这个最强版本，避免树立容易反驳的稻草人。

### 3. 输出格式

| 假设 | 最强成立理由 | Fails if：什么情况下失败 | 本周需要的证据 | 停止或转向标准 | 最便宜的测试 |
|---|---|---|---|---|---|
| {{承重假设}} | {{理由}} | {{具体、可证伪条件}} | {{数据、访谈或实验}} | {{阈值}} | {{最小验证动作}} |

不要生成二十条通用风险。五条能够改变决策的承重假设，比一份冗长风险清单更有价值。

## 九、哪些检查可以自动化

### 适合结构化检查

- 必填章节或条件章节是否缺失。
- 最终文档是否残留占位符、TODO 或模板说明。
- 章节是否为空或只有“无”。
- P0、FR、BR、EX、AC 等 ID 是否重复或引用不存在。
- 每个 P0 是否映射到功能需求、用户动线和验收标准。
- 验收是否包含 Given、When、Then 或等价结构。
- 指标是否缺少定义、数据来源或观察周期。
- 性能描述是否只使用“快、流畅、稳定”等模糊词。
- AI 需求是否缺少 AI 边界和质量评估章节。
- 敏感数据需求是否缺少数据和隐私章节。
- 文档复杂度与实际加载章节是否一致。
- 代码块、表格和 Markdown 结构是否完整。

### 必须由产品经理或相关负责人判断

- 问题是否真实且值得解决。
- 证据是否足以支撑当前结论。
- 核心用户和场景是否选择正确。
- MVP 取舍是否符合业务阶段和资源。
- 指标目标是否合理。
- 哪些风险可以接受。
- AI 可以自主到什么程度。
- 隐私、合规和供应商策略是否满足要求。
- 方案是否值得投入，而不只是能够实现。

自动检查只能发现结构缺口，不能证明产品判断正确。

## 十、修复规则

### AI 可以直接修复

- 删除空章节、模板注释和重复段落。
- 将模糊验收改写成可观察结果，但不得编造目标值。
- 补充根据现有流程可以确定的空状态、失败反馈和恢复步骤。
- 将过度具体的实现要求降为推荐默认或发挥空间。
- 修复 ID、引用、表格和章节结构问题。
- 合并重复规则，保留稳定引用关系。

### AI 必须请求确认或保留开放问题

- 修改核心用户、场景、产品目标或非目标。
- 增加、删除或调整 P0。
- 设定业务指标目标和风险阈值。
- 放宽 AI 真实性、人工确认或隐私边界。
- 接受高影响风险或关闭阻塞依赖。
- 在冲突方案中替产品经理做选择。

## 十一、独立评审输出格式

```markdown
# PRD 质量评审：{文档名称}

**文档类型：** {正式 PRD｜假设草案}
**复杂度：** {简单｜标准｜复杂}
**评审结论：** {拒绝进入下一阶段｜需要重要修订｜可进入讨论｜可进入正式评审｜可研发交接}
**问题数量：** {P0: X，P1: Y，P2: Z，P3: W}

## P0 问题

### F-01：{问题标题}
**位置：** {章节或行号}
**问题：** {准确描述缺口或矛盾}
**为什么重要：** {如果不修复会造成什么后果}
**修复建议：** {具体需要补充、删除、重写或确认什么}
**建议负责人：** {产品｜设计｜研发｜测试｜数据｜合规}

## P1 问题

{同一结构}

## P2 / P3 问题

{同一结构，可适当简化}

## 承重假设

{列出最值得优先验证的 3—5 项}

## 当前成立的部分

{只写经检查能够成立的关键结构，不做空泛表扬}

## 无法评估的部分

{说明缺少哪些资料或决策，以及影响}

## 建议下一步

{修订、补证据、验证假设、重新评审或进入下一阶段}
```

评审报告以问题为主，不自动把 PRD 重写成另一份风格不同的文档。

## 十二、最终自检

- [ ] 已明确当前执行的是生成自检还是独立评审。
- [ ] 已根据文档类型和复杂度选择适用检查项。
- [ ] 已先检查 P0 硬阻塞项，再检查普通质量项。
- [ ] 每个发现都有具体位置、实际影响和可执行修复建议。
- [ ] 没有通过平均分掩盖 P0 或 P1。
- [ ] 已完成跨章节一致性检查，不只是逐章检查。
- [ ] 标准或复杂 PRD 已检查 3—5 个承重假设。
- [ ] 自动修复没有替产品经理做产品决策。
- [ ] 最终质量状态与发现严重程度一致。
